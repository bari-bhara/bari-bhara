# 0009 — Scheduled charge generation with pg_cron

- **Status:** Accepted
- **Date:** 2026-10-24

## Context
Rent was generated by a landlord pressing **Generate rent** each month ([Plan 0001](../plans/0001-initial-architecture-and-roadmap.md), Phase 4). That kept the app free of background jobs: [ADR 0004](0004-unified-charges-table-and-derived-overdue.md) derives overdue status precisely so nothing needs a scheduler, and [ADR 0001](0001-supabase-as-backend.md) rules out a service-role key in the app. Landlords asked for rent and fixed bills to appear on their own ([Plan 0003](../plans/0003-feedback-round-1.md), Part 3).

## Decision
- We will run **`pg_cron` inside the Supabase database**. A job (`bari-bhara-charge-schedule`, hourly at :07) calls `private.run_charge_schedule()`, a `security definer` function with no API exposure.
- For each organization it bills the **current month in the organization's time zone**, so charges appear in the first hour of the 1st wherever the landlord is. Running hourly also picks up tenancies that start mid-month, as the Generate button always did.
- The scheduler never re-creates a charge the landlord **voided**: a type already billed for that tenancy and month, voided or not, is skipped. The Generate button stays as a fallback and can re-create voided charges, as before.
- The same job keeps each active tenancy's `monthly_rent` equal to its scheduled rent ([ADR 0010](0010-unit-charge-schedules.md)), so pages show the rent in force once a change takes effect.
- Activity is logged as before (`RENT_GENERATED`, with no actor for scheduled runs).

## Alternatives considered
- **Vercel Cron calling an API route:** needs a secret-bearing route and a service-role key or a machine user, which ADR 0001 rules out.
- **Supabase Edge Function on a schedule:** another runtime to deploy and monitor, and it would still need elevated credentials.
- **Generate lazily when a page loads:** charges would only exist after someone opens the app, so reminders and dashboards would be wrong until then.

## Consequences
- Hosted Supabase must have the `pg_cron` extension enabled; the migration enables it. The runbook notes how to check the job (`cron.job`, `cron.job_run_details`).
- Failures are visible in `cron.job_run_details`, not in the app. A missed run self-heals on the next hour.
- Tests call `private.run_charge_schedule()` directly instead of waiting for the clock.
